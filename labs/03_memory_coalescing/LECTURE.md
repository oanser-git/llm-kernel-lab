# Lecture: Warp Addresses, Memory Coalescing, And Transaction Efficiency

Read this before implementing Lab 03. The goal is to learn how to predict the
addresses generated by one warp and connect those addresses to measured memory
transactions. This lecture does not provide a complete implementation.

## 1. What Changes After Vector Addition

Lab 02 established a contiguous streaming pattern:

```text
lane 0 reads input[0]
lane 1 reads input[1]
lane 2 reads input[2]
...
lane 31 reads input[31]
```

The arithmetic in Lab 03 can remain trivial. The new variable is the mapping
from a logical thread to a physical memory address.

Two kernels can:

```text
produce exactly the same logical output
request the same number of useful bytes
perform the same amount of arithmetic
```

and still have very different performance because their warp lanes generate
different address patterns.

The central question is:

> When 32 lanes issue a memory instruction, how many memory sectors or
> transactions are needed to serve their addresses?

## 2. Five Levels That Must Not Be Confused

Memory behavior can be discussed at several levels:

| Level | Meaning |
|---|---|
| Logical element | The value required by the algorithm |
| Lane address | The byte address requested by one active warp lane |
| Warp request | The set of lane addresses for one memory instruction |
| Cache transaction | The sectors or cache lines needed to serve the request |
| DRAM traffic | Data that reaches physical memory after cache behavior |

For example, one lane reading one FP32 value creates:

```text
one logical 4-byte read
```

It does not guarantee:

```text
one independent 4-byte DRAM transaction
```

The GPU combines lane requests, uses caches, and transfers data at a larger
granularity than a single float.

This lab starts with logical addresses and then uses profiler evidence to study
the lower levels.

## 3. The Warp Is The Important Unit

A warp contains 32 lanes on this GPU. Coalescing describes how the memory
addresses from those active lanes are combined.

Consider a kernel with:

```text
global_index = blockIdx.x * blockDim.x + threadIdx.x
value = input[global_index]
```

For an aligned FP32 input and the first warp:

| Lane | Element index | Byte offset |
|---:|---:|---:|
| 0 | 0 | 0 |
| 1 | 1 | 4 |
| 2 | 2 | 8 |
| 3 | 3 | 12 |
| ... | ... | ... |
| 31 | 31 | 124 |

The warp requests 32 adjacent floats:

```text
32 lanes * 4 bytes = 128 useful bytes
```

The important property is not simply that each address is valid. The property
is that neighboring lanes access neighboring addresses.

## 4. Definition Of Coalescing

A warp memory access is coalesced when the active lanes' addresses can be
served with a small number of memory transactions relative to the useful data
requested.

Good coalescing usually has these properties:

```text
neighboring active lanes access neighboring elements
addresses are naturally aligned
few transferred bytes are unused
```

Poor coalescing usually involves:

```text
large strides between lanes
irregular gather addresses
misaligned warp footprints
only a few useful bytes in each transferred sector
```

Coalescing is a warp-level property. An individual lane cannot be described as
coalesced by itself.

## 5. Sectors And Transaction Granularity

Modern NVIDIA memory analysis commonly describes global-memory requests using
32-byte sectors. Exact cache-line and transaction behavior depends on the GPU,
cache level, instruction, and profiler metric, so do not treat a simplified
sector model as a complete physical description.

The model is still useful for prediction.

An aligned warp reading 32 FP32 values requests 128 consecutive bytes:

```text
sector 0: bytes   0-31
sector 1: bytes  32-63
sector 2: bytes  64-95
sector 3: bytes 96-127
```

For this unique-address load, idealized per-request input-sector utilization is:

```text
lane-requested useful load bytes / bytes covered by requested sectors
= 128 / 128
= 100%
```

This sector count does not establish how many bytes transfer at every cache
level or reach DRAM. Sectors may be served from a cache, combined into a larger
request, or shared with another warp request. It only predicts that this one
warp instruction uses its covered sectors well.

## 6. Contiguous Access Baseline

The baseline mapping is:

```text
physical_index(lane) = warp_start + lane
```

For FP32:

```text
byte_address(lane)
    = base_address + 4 * (warp_start + lane)
```

Lane-to-lane byte distance is:

```text
4 bytes
```

This pattern is the reference for the offset, stride, and gather experiments.
Use the same logical element count and the same useful-byte definition whenever
possible.

The four-sector prediction assumes the warp's first byte is 32-byte aligned.
`cudaMalloc` aligns the allocation base, but a later block can start off a
sector boundary when `blockDim.x * sizeof(float)` is not a multiple of 32.
Partial warps also request fewer useful bytes. Predict full aligned warps first,
then account for block starts and the final partial warp separately.

## 7. Alignment And Offset Access

`cudaMalloc` returns a strongly aligned base allocation. That does not mean
every address derived from that base remains aligned for a warp footprint.

Suppose the base is aligned and the kernel reads:

```text
input[global_index + offset]
```

### Offset Zero

The first warp reads byte offsets:

```text
0, 4, 8, ..., 124
```

It fits in four aligned 32-byte sectors.

### Offset One Float

The first warp reads byte offsets:

```text
4, 8, 12, ..., 128
```

The useful bytes now cross the original 128-byte boundary. In the simplified
sector model, the request touches five sectors:

```text
bytes   0-31: partially used
bytes  32-63: used
bytes  64-95: used
bytes 96-127: used
bytes 128-159: partially used
```

For a warp whose unoffset start was sector-aligned, per-request input-sector
utilization becomes:

```text
128 useful bytes / 160 sector bytes
= 80%
```

### Offset Eight Floats

Eight FP32 values occupy 32 bytes:

```text
8 * 4 = 32 bytes
```

An offset of eight floats moves the starting address to another sector
boundary, so the warp can again fit in four sectors, assuming the base was
appropriately aligned.

The lesson is:

> Aligned allocation does not guarantee that every effective address pattern
> is aligned or transaction-efficient.

Sequential offset warps can cover a common boundary sector. Therefore, five
covered sectors per warp does not imply five new DRAM sectors for every warp;
cache state and overlap between requests affect lower-level traffic.

## 8. Strided Access

A strided mapping is:

```text
physical_index(lane) = logical_index * stride
```

For the first warp:

```text
physical_index(lane) = lane * stride
```

The lane-to-lane byte distance for FP32 is:

```text
stride * 4 bytes
```

### Stride One

```text
lane indices: 0, 1, 2, 3, ..., 31
byte offsets: 0, 4, 8, 12, ..., 124
```

The pattern is contiguous.

### Stride Two

```text
lane indices: 0, 2, 4, 6, ..., 62
byte offsets: 0, 8, 16, 24, ..., 248
```

The warp still requests 128 useful bytes, but they span 252 bytes of address
space and cover eight aligned sectors totaling 256 bytes:

```text
128 useful bytes / 256 sector bytes
= 50% idealized sector efficiency
```

### Stride Four

```text
lane indices: 0, 4, 8, 12, ..., 124
byte distance between lanes: 16 bytes
```

The warp touches approximately 16 sectors in the aligned simplified model:

```text
128 useful bytes / 512 sector bytes
= 25% idealized sector efficiency
```

### Stride Eight

```text
byte distance between lanes = 8 * 4 = 32 bytes
```

Each lane lands in a different 32-byte sector:

```text
32 lanes * 32 sector bytes = 1024 sector bytes
128 useful bytes / 1024 sector bytes = 12.5%
```

For still larger strides, one warp cannot require more than one distinct
sector per active lane for a single 4-byte load, but cache-line and DRAM
behavior can continue to change.

These are predictions, not substitutes for profiler measurements.

## 9. Warp Footprint Formula

For a full warp loading FP32 values with positive stride `S`, the lowest and
highest requested byte offsets are:

```text
lowest  = 0
highest = 31 * S * 4
```

The span containing the final four-byte value is:

```text
span_bytes = (31 * S + 1) * 4
```

Examples:

| Stride | Span |
|---:|---:|
| 1 | 128 bytes |
| 2 | 252 bytes |
| 4 | 500 bytes |
| 8 | 996 bytes |

The span is not always equal to bytes transferred because there can be holes
between requested sectors. Use it to understand how far addresses spread, not
as an exact traffic formula.

## 10. Gather Access

A gather obtains the physical address from an index array:

```text
physical_index = indices[logical_index]
output[logical_index] = input[physical_index]
```

One logical element may require:

```text
read one index
read one input value at the indexed location
write one output value
```

If both the index and value are 32 bits, a useful-byte model can be:

```text
4-byte index read
4-byte value read
4-byte output write
-------------------
12 useful bytes per logical element
```

State the convention in the report. If comparing only the gathered value
loads, report that narrower convention explicitly instead.

Do not apply `lane-requested bytes / unique sector bytes` as a general gather
efficiency formula when lanes can request duplicate addresses. If all lanes
read the same float, there are 128 lane-requested bytes but only one unique
4-byte value in one sector. Report duplicate-address behavior separately and
use profiler counters to describe the actual request handling.

### Contiguous Indices

```text
indices = [0, 1, 2, 3, ...]
```

The gathered input addresses are contiguous and can coalesce well.

### Permuted Nearby Indices

```text
indices = [3, 0, 2, 1, ...]
```

Lane order is irregular, but addresses may still fall in a small number of
sectors. Coalescing depends on the set of addresses, not whether lane order is
monotonically increasing.

### Widely Scattered Indices

```text
indices = [0, 1024, 7, 90000, ...]
```

The warp may touch many sectors and cache lines, producing poor transaction
efficiency and low useful bandwidth.

## 11. Logical Layout Versus Physical Address

Correctness validation must distinguish where an output appears logically from
where its input came from physically.

For a strided copy:

```text
output[logical_index] = input[logical_index * stride]
```

The CPU reference must use the same mapping:

```text
expected[logical_index] = input[logical_index * stride]
```

Do not compare `output[i]` with `input[i]` when the kernel intentionally uses a
different physical address.

The same rule applies to offset and gather variants:

```text
offset: expected[i] = input[i + offset]
gather: expected[i] = input[indices[i]]
```

## 12. Safe Allocation Sizes

Address experiments easily become out-of-bounds experiments by accident. Size
the physical input for the largest index, not just the logical output length.

Treat `N == 0` as a separate no-work case. The formulas below assume `N > 0`;
otherwise `N - 1` can underflow when `N` is unsigned.

### Contiguous Input

For `N` logical elements:

```text
largest index = N - 1
required input elements = N
```

### Offset Input

For nonnegative offset `O`:

```text
largest index = (N - 1) + O
required input elements = N + O
```

### Strided Input

For positive stride `S`:

```text
largest index = (N - 1) * S
required input elements = (N - 1) * S + 1
```

Example:

```text
N = 1000
stride = 8
required elements = 999 * 8 + 1 = 7993
```

### Gather Input

Every index must satisfy:

```text
0 <= indices[i] < input_element_count
```

Validate the index array on the CPU before launching the kernel.

Use sufficiently wide unsigned types for host allocation arithmetic and device
index arithmetic. Before evaluating the formulas, check every addition and
multiplication for overflow, including:

```text
N + offset
(N - 1) * stride + 1
required_elements * sizeof(element)
```

Using `std::size_t` alone does not prevent overflow. A large stride can make the
physical allocation much larger than the useful logical output.

## 13. Element Width And Vector Width

The same lane index pattern produces different byte footprints for different
element sizes.

For a contiguous full warp:

| Element | Bytes per lane | Useful warp bytes |
|---|---:|---:|
| `uint8_t` | 1 | 32 |
| `half` | 2 | 64 |
| `float` | 4 | 128 |
| `double` | 8 | 256 |

A vectorized type such as `float4` requests 16 bytes per lane. A full warp then
requests 512 useful bytes. Vectorization changes instruction count and address
width, but it does not remove alignment, bounds, or coalescing requirements.

Do not add vectorization until scalar address patterns are correct and
measured. It is an independent variable and can obscure the lesson.

## 14. Structure Of A Fair Experiment

Change one address-pattern variable at a time.

A useful sequence is:

```text
same N
same data type
same block size
same warm-up count
same repetition count
same useful-byte convention
different stride or offset only
```

Then separately sweep block size or element width.

If stride changes the physical allocation size, report both:

```text
logical elements processed
physical input elements allocated
```

This prevents a large-stride experiment from appearing equivalent in memory
capacity to the contiguous baseline.

## 15. Timing Method

Use the Lab 02 method:

```text
allocate and initialize outside timing
copy inputs H2D outside timing
run untimed warm-up launches
record start event
launch the kernel many times
record stop event
synchronize the stop event
divide total milliseconds by repetitions
copy output D2H outside timing
validate every logical output
```

Do not run Compute Sanitizer or Nsight Compute while collecting final timing
numbers. Instrumentation changes execution time.

Do not run different benchmark processes concurrently. They would compete for
the same GPU resources.

Repeated launches over the same buffers measure warmed steady-state behavior.
The event interval also includes any gaps between queued launches. For small
working sets or very short kernels, this can differ from cold-streaming
behavior or an isolated launch, so record the working-set size and repetition
method.

## 16. Useful Bandwidth

A simple copy or transform that reads one FP32 value and writes one FP32 value
has this useful-byte model:

```text
read input[i]    4 bytes
write output[i]  4 bytes
------------------------
useful bytes     8 bytes per logical element
```

For `N` logical elements:

```text
useful bytes = 8 * N
```

Effective useful bandwidth is:

```text
GB/s = useful bytes / average seconds / 1e9
```

The numerator remains `8 * N` for contiguous and strided copy variants if both
produce the same `N` logical outputs. Lower strided bandwidth is consistent
with wasted sector capacity, but timing alone does not prove that cause. Cache
behavior, TLB pressure, partition mapping, latency, and launch overhead can also
change performance. Use sector and byte counters for attribution.

Do not replace the numerator with the size of the large strided allocation.
Most of that allocation may never be requested.

## 17. Requested Bytes Versus Transferred Bytes

Useful bandwidth counts bytes required by the algorithm. Sector analysis asks
which 32-byte regions a warp instruction covers. Cache-line fills, interconnect
transfers, and DRAM transactions are related but distinct, architecture-level
events.

For the unique-address input loads below, define idealized input-load sector
utilization:

```text
input-load sector utilization
    = lane-requested load bytes / bytes covered by requested sectors
```

Example predictions for one aligned FP32 warp load:

| Pattern | Useful load bytes | Covered sector bytes | Load-sector utilization |
|---|---:|---:|---:|
| Stride 1 | 128 | 128 | 100% |
| Stride 2 | 128 | 256 | 50% |
| Stride 4 | 128 | 512 | 25% |
| Stride 8 | 128 | 1024 | 12.5% |

These predictions cover only the strided input load, not the contiguous output
store in an `8 * N` copy kernel. For example, the stride-two input load has 50%
sector utilization, while a simplified combined load-plus-store calculation is:

```text
(128-byte useful load + 128-byte useful store)
/
(256 covered input-sector bytes + 128 covered output-sector bytes)
= 66.7%
```

These predictions describe a cold simplified sector-coverage model. Profiler
values can differ because of cache reuse, overlapping sectors between warps,
partial warps, duplicate addresses, instruction details, and metric level.

## 18. Why Cache Hits Complicate Interpretation

Suppose a poorly coalesced first launch fetches many sectors into L2. A repeated
launch may hit those cached sectors instead of reaching DRAM.

Then you can observe:

```text
poor lane address pattern
many sectors requested
high cache hit rate
less DRAM traffic than expected
```

This is not a contradiction. Coalescing and caching answer different questions:

```text
coalescing: how efficiently lane addresses form transactions
caching:    where those transactions are served
```

To study streaming DRAM behavior:

```text
use a working set larger than relevant caches
avoid repeatedly measuring a tiny region
report cache hit rates
compare cold and warmed behavior when useful
```

Your GB10 reports a 24 MiB L2 cache. A tiny working set can measure cache
behavior rather than sustained memory behavior.

## 19. Nsight Compute Workflow

Use timing runs and profiler runs for different purposes.

### Timing Run

```text
many repetitions
minimal output
no profiler
report stable average latency and GB/s
```

### Profiler Run

```text
one or a few kernel launches
one selected configuration
collect memory workload and source counters
```

A starting command is:

```bash
ncu --section MemoryWorkloadAnalysis \
    --section SourceCounters \
    ./memory-coalescing
```

Compile profiler builds with line information when source correlation is
needed:

```bash
nvcc -std=c++17 -arch=native -lineinfo memory-coalescing.cu \
    -o memory-coalescing
```

If the executable launches many kernels, select the kernel and limit launches.
The exact filters depend on the installed Nsight Compute version:

```bash
ncu --help
ncu --query-metrics
```

Look for evidence conceptually related to:

```text
global load/store requests
sectors per request
L1 and L2 hit rates
L1/L2 bytes
DRAM bytes
memory throughput
```

Metric names and availability vary by GPU and Nsight Compute release. Record
the actual names used in `REPORT.md` rather than copying names from another
architecture.

Nsight Compute may replay a kernel to collect multiple metric groups, and its
cache-control settings can change cache state relative to an unprofiled timing
run. Record replay and cache-control behavior from the profiler output when
interpreting hit rates or DRAM bytes.

## 20. What To Predict Before Profiling

For each configuration, write a prediction before running it:

| Pattern | Prediction |
|---|---|
| Contiguous aligned | Few sectors, high useful bandwidth |
| Offset by one float | Extra boundary sector for full warps whose original start was sector-aligned |
| Offset by sector width | Similar to aligned baseline |
| Stride 2 | More sectors, lower useful bandwidth |
| Stride 8 | About one sector per active lane |
| Contiguous gather indices | Similar gathered-value pattern to contiguous |
| Random gather indices | Many sectors and poor locality |

After profiling, explain disagreements instead of changing the prediction
silently. Cache behavior, partial warps, and compiler-generated instructions
are common reasons.

## 21. Coalescing In LLM Workloads

### Embedding Lookup

Token IDs gather rows from an embedding table. Threads may read contiguous
features within one selected row, while different tokens select distant rows.
The layout and assignment of lanes determine whether feature reads coalesce.

### KV Cache

Attention reads keys and values across token, head, batch, and feature
dimensions. A layout contiguous for one dimension may be strided for another.
Decode performance depends strongly on which dimension neighboring lanes walk.

### Quantized Weights

Packed low-bit values and scale metadata require carefully aligned loads.
Irregular group layouts can increase transactions even when the allocation base
is aligned.

### Matrix Multiplication

Rows are contiguous in row-major storage, while columns are strided. Tiled GEMM
uses cooperative loads and shared memory partly to turn difficult global access
patterns into coalesced transactions with data reuse.

### Batching And Scheduling

Variable-length sequences and indirection tables can create gather-like
addresses. Grouping requests with compatible shapes can improve locality.

## 22. Common Misconceptions

### "Every Thread Reads Four Bytes, So Every Read Costs Four Bytes"

Four bytes is the useful logical request. Physical transfers occur in larger
units and are shared across lanes.

### "cudaMalloc Is Aligned, So Access Is Coalesced"

The base is aligned. Offsets, strides, and gather indices determine effective
addresses.

### "Stride Is Only A Bounds Problem"

A strided kernel can be fully in bounds and mathematically correct while using
memory transactions inefficiently.

### "More Threads Fix Poor Coalescing"

More warps can hide latency, but they do not change the addresses generated by
one warp. Poor transaction efficiency can remain.

### "High Cache Hit Rate Means Good Coalescing"

Cache hits can make repeated poor requests cheaper. They do not make the lane
address pattern contiguous.

### "Bandwidth Is Exact DRAM Traffic"

Useful GB/s is an algorithm-level rate. Use profiler metrics to study cache and
DRAM traffic.

## Final Takeaway

Memory bandwidth is not determined only by how many useful bytes the algorithm
needs. It also depends on how warp lanes place those bytes into memory
transactions.

The skill to carry forward is:

> Given a tensor layout and a thread mapping, write the address requested by
> every lane in one warp, predict transaction efficiency, and verify the
> prediction with measurements and profiler evidence.
